## 1. ~~Statut « en stock constructeur » mais non commandable~~ — ✅ CORRIGÉ ET VALIDÉ le 23/09

**Ce n'était pas un bug de règle : le blocage vient d'une demande explicite du client
(spec §13). Le défaut était le libellé.**

**Correction livrée** : dans la branche `backorder`, quand la date est future, le texte
devient « **Commandable à partir du [date]** » au lieu de « Dispo. le [date] ». La règle
`msCommandable` n'est pas touchée — aucun produit ne change de commandabilité. Voir
spec §15.

**Validé en préprod le 23/09** sur fiche produit, carte de listing et cas limite (date = jour même).

Restent ouverts, tous deux sur la RÈGLE et non sur l'affichage :
- l'arbitrage « précommande » du §3 cas 4 ;
- le trou du §16 — la règle ne s'applique pas aux produits à déclinaisons (135 produits, 0 déclinaison datée sur 5 090).

Règle en vigueur ([product.tpl:88-89](../megaservice/templates/catalog/product.tpl#L88-L89)
et son équivalent dans la miniature) :

```smarty
{assign var='msDateFuture'  value=($product.available_date > $msToday)}
{assign var='msCommandable' value=($product.add_to_cart_url && !$msDateFuture)}
```

Le bouton d'achat est **délibérément bloqué tant que la date de réassort annoncée
n'est pas atteinte** (commit `6b070e6`).

### Vérification sur la référence de test `00010000348` (id 94496)

| Champ | Valeur |
|---|---|
| `active` / `available_for_order` / `show_price` | 1 / 1 / 1 |
| `quantity` | 0 |
| `available_date` | **2026-09-18** |

Le COPROJ s'est tenu le **17/09**, soit la veille. La date était donc dans le futur →
bouton désactivé, pendant que le bandeau affichait « Dispo. le 18/09/2026 ». Le client
a vu une promesse de disponibilité à côté d'un bouton verrouillé sans explication.

### Le vrai sujet : 1 874 produits dans cet état aujourd'hui

| Situation (au 22/09) | Produits |
|---|---|
| Commandables, date de réassort **future** → bouton bloqué | **1 874** |
| Commandables, date passée ou absente → bouton actif | 44 806 |

Ce n'est donc pas un cas isolé, et ça se reproduira en permanence.

### Ce qui est à trancher, pas à coder

La question rejoint l'arbitrage « précommande » déjà en attente (spec §3 cas 4) :

- soit on **assume le blocage** et on explique le refus au client (« commandable à partir du 18/09 » plutôt qu'un bouton mort),
- soit on **ouvre la précommande** sur la date annoncée.

**Aucune modification de code avant cet arbitrage** — la spec l'interdit explicitement.
Prévoir de confirmer au client que c'est bien ce cas qu'il a vu au COPROJ.

## 2. Régression JS — filtres PowerParts inactifs

**Analyse statique menée à fond le 23/09. Cinq causes éliminées. Bloqué sur une
reproduction navigateur.**

### Ce qui est ÉLIMINÉ, preuves à l'appui

| Piste | Verdict |
|---|---|
| `filters.js` du thème | Ne gère que le bottom-sheet mobile et le toast — aucun rôle dans le filtrage |
| `microfiches-plp.js` chargé partout | Correctement borné : sort immédiatement si `.js-ms-plp-grid` absent, aucun handler capture |
| Notre `facets.tpl` divergerait du natif | **Diff = 1 seule ligne**, le libellé du bouton « Réinitialiser ». Balisage identique à `themes/classic` |
| jQuery UI manquant pour le slider prix | Le module le charge lui-même : `addJqueryUi('ui.slider')` dans `src/Hook/ProductSearch.php`, et `PS_USE_JQUERY_UI_SLIDER = 1` |
| Un chemin de clic non couvert | `app.js` intercepte en **phase capture** : `a.js-search-link`, clic sur la case dans `.facet-label`, bouton « Effacer tout », liens des filtres actifs. Les quatre chemins sont gérés |

### Ce qui est établi

- Le thème a sa **propre implémentation AJAX** des facettes (`fetchFacetUpdate` dans `app.js`),
  qui court-circuite celle du module par `stopImmediatePropagation()`. Elle date du **25/04**.
- `ps_facetedsearch` 4.0.2 : son `views/dist/front.js` ne contient ni `facet-label`, ni
  `js-search-link`, ni `search_filters` — il ne pilote donc pas les cases, seulement le slider.
- Facettes configurées sur le sous-arbre Powerparts (cat 41, 332, 369) : `category`,
  `availability`, `extras`, `manufacturer`, `price` — **toutes en checkbox**.
- **Les filtres ont été configurés le 28/07**, bien après le code d'avril. Le défaut n'est donc
  pas une modification récente de notre code : ce sont les facettes qui sont apparues.

### Piste restante, non vérifiable sans navigateur

Le hook `actionFacetedSearchFilters` du module montabilité injecte `id_product IN (...)` dans la
requête des facettes quand un filtre moto est actif — et force un résultat **vide** si la moto
n'a aucune compatibilité. Jusqu'au 23/09, le bouton « Réinitialiser » ne vidait pas le cookie
serveur : un cookie moto résiduel pouvait donc fausser facettes et compteurs pendant le COPROJ
du 17/09. À écarter en testant **en navigation privée**.

### Ce qu'il me faut pour avancer

L'un ou l'autre :
- le **message d'erreur exact de la console** au clic sur un filtre qui ne réagit pas ;
- les **identifiants Basic Auth** de la préprod, pour reproduire moi-même.

Sans ça, toute suite serait de la conjecture : le code est conforme au natif sur les cinq
chemins vérifiés.
